# Extension SDK V1

The Extension SDK V1 is the first executable contract between Agentic Security Harness
and optional security components. It lets an operator pass validated, privacy-minimized
`CanonicalObservationEventV1` records through explicitly registered checks and receive
content-bound findings and receipts.

This source-level contract is under review on the Extension SDK branch. It is not part of
the published `1.2.0` package until a later release gate says so.

## What the contract provides

- a closed extension manifest with an exact extension id, version, component id,
  Harness API range, implementation and configuration digests, capabilities, consumed
  contracts, and produced contracts;
- a closed observation envelope that reuses the existing portfolio observation event and
  commitment rather than inventing another telemetry shape;
- a closed finding/result contract whose evidence references must resolve to events in
  the input envelope;
- deterministic run and pipeline receipts that bind every input and output transition;
- an explicit in-memory registry and ordered runner for operator-approved extension
  objects;
- JSON Schemas plus a content-bound contract manifest generated by
  `tools/extension_contracts.py`.

The required V1 dataflow is:

```text
validated CanonicalObservationEventV1 records
    -> ExtensionObservationEnvelopeV1
    -> explicitly registered ExtensionV1 object
    -> ExtensionResultV1 + output envelope
    -> ExtensionRunReceiptV1
    -> ExtensionPipelineReceiptV1
```

Every accepted extension consumes `portfolio-observation@1.0`, produces
`extension-finding@1.0`, declares `observation.read` and `finding.emit`, and retains
`operational_authority=none`.

## Inspect a manifest without loading code

```bash
ash extension-inspect path/to/extension-manifest.json --format text
ash extension-inspect path/to/extension-manifest.json --format json
```

The inspector accepts only a bounded canonical JSON object, rejects duplicate or unknown
fields, and rejects unsafe file topology. It prints a sanitized manifest summary and
`code_loaded=false`. It does not import the extension, inspect installed entry points,
contact a registry, or execute provider traffic.

Generate or verify the committed contract artifacts:

```bash
python tools/extension_contracts.py generate
python tools/extension_contracts.py check
```

## Trust boundary

`run_extension_v1()` executes an already constructed Python object in the Harness
process. The object is selected by the operator and registered explicitly. This is an
integration and conformance boundary, not a sandbox or a package trust decision.

V1 intentionally has no:

- automatic entry-point discovery or arbitrary module import;
- package download, dependency resolution, signature verification, or allowlist service;
- subprocess, container, WASM, or operating-system isolation;
- network or provider transport;
- credential, secret, deployment, release, enforcement, or tool-execution authority.

A malicious approved Python object still runs with the permissions of the Harness
process. Future installable-extension work must bind distribution identity, version,
manifest digest, dependency provenance, operator approval, and an isolation model before
code loading is added.

The V1 implementation and configuration digests are content pins supplied by the
extension builder and bound into every result through the manifest digest. They are not a
signature or proof that the named package was installed; the operator/discovery layer must
verify those pins before registering code.

## Determinism and privacy

The V1 runner deep-copies the envelope before invoking an extension and rejects detected
input mutation. It bounds event, finding, chain, and serialized payload sizes. A manifest
that declares deterministic behavior must also declare `network_mode=off`.

Public observations must remain privacy-minimized. The contract carries typed ids,
digests, classifications, advisory findings, and bounded metadata; it does not create a
new place for raw prompts, raw model output, credentials, private paths, or unrestricted
tool payloads.

## Current and next integration state

The SDK is the core contract slice. Companion repositories remain standalone or
contract-only until each one has a source-owned adapter, synthetic conformance tests, and
an exact compatibility row. Adding a README link or a manifest alone does not make a
component installable.

The next reviewed slices are:

1. Harness-owned adapters for transfer verification, handoff checks, and declarative
   playbooks using this exact envelope;
2. a pinned, operator-approved distribution discovery layer with no implicit code load;
3. Linux and Windows cross-repository compatibility fixtures;
4. provider-neutral security-intelligence collectors whose outputs remain advisory-only.

Passing these synthetic tests does not establish independent detector effectiveness or
production safety.
